# Round 1 survey: 7. Accessibility bridges

Measured with a hidden-HWND rig around the real `WindowsAccessibilityBridge` plus the perf
suite's `a11y/` rows (worktree agent-a13a53b90456885b4, 7f8e846). The Linux estimate is
from field layout; builds were blocked after the session restart.

SATISFIED: no
REVIEW: none (round 1)

## Candidates

- **a11y-uia-wrapper-rebase.** After each diff, point every surviving UiaFragment at its node in the new tree in one lookup-only walk; drop the per-diff full-tree `currentById` dictionary.
  - Evidence: `UiaFragment.Node` (UiaFragment.cs:25) is reassigned only for added, property-changed and refreshed-parent nodes (WindowsAccessibilityBridge.cs:395-403, 416-418, 463-469); other wrappers keep old nodes whose Parent/Children links keep whole old trees alive. 500 checkbox rows (1,001 nodes): 50 toggles retained 51 trees / 8.4 MB; 200 toggles 201 trees / 34.2 MB (~170 KB per tree); worst case O(n²). Rebasing → 1 tree. IndexTree (:391-392, :450-455) builds a new Dictionary per diff: 47 KB per keystroke at 603 nodes, 211 KB per rebuild at 2,001–3,001 nodes (23–30 % of a11y bytes). Side effect: sibling navigation reads the stale tree (UiaFragment.cs:246-259) — wrong NextSibling after insert/remove.
  - Expected: leak closed (34 MB → ~0); −47 KB per keystroke (−18 %), −211 KB per rebuild (−30 % of a11y bytes).
  - Proof: Headless test that wrappers hold 1 tree after N toggles; sibling-navigation test; existing UIA tests (PasswordUiaTests, UiaTextPatternTests, TabRolesUiaTests, NativeContentUiaTests); events unchanged. Needs a Windows-only suite row with the real bridge on a hidden HWND.
  - Cost: small. UIA sibling navigation becomes correct.
- **a11y-build-diff-garbage.** Index loops instead of `foreach` over `IReadOnlyList<Element>` (AccessibilityTreeBuilder.cs:109, 353, 382); node children list created on first AddChild (AccessibilityNode.cs:79); differ matches children by position while ids agree, dictionary only from the first mismatch (AccessibilityTreeDiffer.cs:52-58); presize children arrays; owner slot looked up once per list (AccessibilityTreeBuilder.cs:232 → AccessibleOwnerSlots.cs:44, a lock per item).
  - Evidence: 1,000 benchmark rows (3,001 nodes): build 690,016 B = 230 B/node (168 B node incl. empty 32 B List on leaves; 120 KB boxed enumerators; ~33 KB array growth). Diff of an unchanged tree: 121,664 B, 0 changes. Eager 2,000-item VirtualList: 2,000 slot locks + 2,000 GetItemLabel per rebuild. a11y/edit every 10th of 1,000: 627 KB/op.
  - Expected: that row 627 → ~425 KB/op (−32 %); rebuilds ~40 % lighter (build 230 → ~140 B/node, diff 40 → 0 B/node).
  - Proof: AccessibilityTreeDifferTests, TreeDiffCoalescingTests, Headless a11y tests; new zero-alloc unchanged-diff test; randomized old-vs-new diff equivalence test.
  - Cost: small.
- **a11y-property-patch.** When a frame's only a11y reasons are element property notifications (no Children flag, no first attach, no layout refresh due), rebuild nodes only for notified elements and their name-from-content ancestors, swap them into the previous tree and diff only those.
  - Evidence: Window.cs:834-835, 842-851 rebuild everything on `_a11yPropertyDirty`; observer (Window.cs:3116-3129) discards the element and property. Bridge on vs off (KB/step): keystroke in TextInput 603 nodes, 1 change, 257 vs 46; checkbox click 1,001 nodes, 346 vs 6; label edit 2,001 nodes, 702 vs 8; keystroke filtering an eager 2,000-item list, 661 vs 6. Every ProgressBar/Slider value set (ProgressBarElement.cs:43, SliderElement.cs:45) forces a full rebuild — animated progress or a playback scrubber is O(n) per frame.
  - Expected: O(n) → O(changed); 603-node form ~208 → ~2 KB a11y bytes per keystroke (−80 % of the step). Linux needs a11y-atspi-snapshot-per-diff too.
  - Proof: test-only shadow mode running full Build+Diff after every patched frame, asserting equal nodes and equal PropertyChanged sets; recorded event streams of existing a11y tests.
  - Cost: large. Name-from-content ancestors, overlay origins; WebView Content and NativeContent fall back; UIA threads read the tree concurrently — single reference swaps only.
- **a11y-atspi-snapshot-per-diff.** Linux bridge reuses previous immutable AtSpiAccessible objects and path strings for untouched nodes instead of republishing the whole snapshot per diff.
  - Evidence: ApplyChanges → Build every diff (LinuxAccessibilityBridge.cs:139, 317-333). Per node: AtSpiAccessible (~150 B), List<string> child paths, path string formatted twice (AtSpiAccessible.cs:115, 122), string-keyed Dictionary insert. ~400 B/node, estimated, not measured.
  - Expected: ≥10 % churn on every Linux a11y rebuild; prerequisite for the property-patch scaling win on Linux.
  - Proof: Linux.Tests (AtSpiState, AtSpiPassword, AccessibleContentBridge), AtSpiVerify bulk + atspi_bulk_verify.py, WSL Fedora `scripts/wsl-test.sh`.
  - Cost: medium; Linux-only verification.
- **a11y-richtext-text-snapshot.** Build the rich text editor's AccessibleText string and line/paragraph tables on first read; differ compares snapshots by document identity + selection, not strings.
  - Evidence: a11y/type in rich text (bridge on) 2,135 KB per keystroke vs richtext/type 86 KB off. 5,000 blocks / 748,576 chars: snapshot 2,109 KB/keystroke; ToPlainText 1,520 KB (RichTextEditorElement.Accessibility.cs:83); LineGeometry presized 2 × blocks (:107); AccessibleText rescans '\n' (AccessibleText.cs:58-62, 66-78); differ compares 748k-char strings (AccessibilityTreeDiffer.cs:115). RichDocument immutable; cache key already reference identity (:63).
  - Expected: 2,135 → ~100–600 KB/op on Windows when the client doesn't read text; Linux only the table/geometry part.
  - Proof: RichTextAccessibilityTests, UiaTextPatternTests, same event stream for typing/caret/selection.
  - Cost: medium; internal lazy ctor for public AccessibleText. Touches text-pipeline expert's editor files.

## Needs the user

- **Bounds events on scroll.** Every on-screen node raises a UIA BoundingRectangle change per coalesced scroll rebuild (WindowsAccessibilityBridge.cs:551), with an empty value (UiaFragment.cs:169-188 has no BoundingRect case). 1,000 rows: 133 events per rebuild, 798 per 30 notches; each costs 3 provider callbacks. Keep per-descendant bounds events, or raise one scroll-position change on the scroll view as browsers do (Chromium's exact UIA mapping not checked)? Changes the event stream.
- **Stale focus state (correctness).** A Tab doesn't rebuild the tree, so HasKeyboardFocus/IsFocused stay stale until the next rebuild, which raises the IsFocused changes late. Fix it (small rebuild or patch per focus move)?
- Real-window count of what the background UIA client queries was not taken (that run was declined); "queried" counts are from the hidden-HWND rig only.
