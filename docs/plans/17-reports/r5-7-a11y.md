## Review

No regression from round 4's build. One older correctness gap became visible through 87e11055; it is folded into candidate 1.

- **Allocation.** All 27 `a11y/` suite rows at HEAD (full 5×5 run) match f14bc82d's capture within 0.1 KB/op. A `--quick` run read differently (for example, edit 1 label UIA 58.8 against 35.8). That is the known step-count trap, not a regression.
- **f14bc82d (restyle marks).** A style-only change cannot reach a11y names or states:
  - `AccessibilityTreeBuilder.CreateNode` (:107-149) reads no resolved style. Its inputs are role, name, description, layout box, focus, `IsEnabledForAccessibility`, toggle/value/selected, range, scroll and text source.
  - The one control state that came through a style-ish path, `ButtonElement._enabled`, notifies since 968bd8d1.
  - The staleness audit found no stale name or state outside overlays. How it works: every window listens; at each frame where nothing is dirty or pending, a fresh tree is compared with the applied one. Coverage: Headless (1,011 tests, 1,275 audits), Junction (989 tests), Vesper (852), Meridian (418), Reel (50), Aperture (296), Fluent (34).
- **87e11055 (overlay open/close rebuild): older gap, now systematic.**
  - The tree is built in the frame after `Show`, before the menu's first `Render`.
  - `ContextMenuElement.ItemBounds` returns null and `ItemHeight` returns 0 until Render fills `_itemYOffsets` (ContextMenuElement.cs:77-84, :314-318). So every menu item node gets a zero-height rect, and nothing refreshes it while the menu is open.
  - Probe: all 4 items' bounds differ from a fresh tree after open. The audit shows the same in Junction's `ContextMenuBorderTests` (STALE BoundingRect).
  - Before 87e11055 a plain context menu was not in the tree at all, so this is not a regression. It goes into candidate 1.
- **No regression found** in 968bd8d1, 1698b4a6, 9218026a, 78f3a22b, 92beae04/07ed97e3/30d19928, 59a11d7d, or in ef0a1f49's keep-layout for themed controls and item-row lists (the audit found no stale tree).
  - a0221337: a keystroke in a 2,000-line TextArea costs +0.7 KB with UIA and +1.1 KB with AT-SPI over bridge off (247.7 → 248.8 / 249.4 KB). The gap between the suite rows "a11y/type in a 2,000-line TextArea, UIA" (259 KB) and "input/type…" (206 KB) comes from their different setups, not from a11y.
- **e2fafa31 note (not a regression).** The leaf patch is skipped whenever a layout refresh comes due in the same frame (Window.cs:1348-1354). `TextElement.Content` always marks layout, so a ticking label still builds a whole tree per tick. This is candidate 2.
- **Harness trap (not a bug).** A recording bridge does not make `AccessibilityClients.Active` true. TextArea and RichTextEditor tell caret moves only when it is true (TextAreaElement.Accessibility.cs:66, RichTextEditorElement.cs:235). The real bridges do report it (WindowsAccessibilityBridge.cs:78-82; Linux :140), and the existing tests set `Force`. My audit's first pass reported false STALE carets until it reported a client.

## Candidates

- **id: a11y-overlay-live** (correctness; replaces a11y-overlay-property-changes)
  - **What:**
    - Overlay content gets the window's `AccessibilityObserver`.
    - The a11y phase sees overlay Children dirt (rebuild now) and layout dirt (coalesced refresh). To make that work, overlay style and layout move ahead of the a11y phase, out of `RenderOverlays`.
    - Patches find nodes under an overlay's subtree, which is a child of the root node.
    - `ContextMenuElement` tells its keyboard and hover selection, and has its item geometry before the tree reads it.
    - AT-SPI sends `state-changed:expandable` when `Expanded` goes to or from null.
  - **Evidence:**
    - Code:
      - `NotifyAccessibilityPropertyChanged` walks `Parent` looking for an observer (Element.cs:810-820), and only the root gets one (Window.cs:1006). `Show` sets the overlay's host and focus manager, not the observer (:2963-2998).
      - `a11yImmediate` and `layoutWasDirty` read only `_root` (:1296, :1339-1340).
      - Overlays are laid out in `RenderOverlays`, after the a11y phase (:3209-3227).
      - `FindNodeDown` returns null outside the root (:900).
    - Probe, inside an open overlay (`Overlays`): changing a label's text, toggling a check box, typing into a TextInput, and a component adding 2 buttons each built 0 trees and sent 0 diffs. The applied tree stayed stale until close: Name/IsToggled/Value differ, and 2 nodes are missing.
    - `CommandPalette` (Junction's and Meridian's Ctrl+P): typing "s" changes the results from 932 to 924 nodes (14 added, 22 removed, Name and Value changes); "a" takes it to 918. 0 trees: a reader keeps the empty query and the open-time list until the palette closes.
    - Context menu, and the Dropdown's list (the same element): two Down keys are never told. `MoveSelection` and `SetHoveredIndex` only mark paint (ContextMenuElement.cs:158-180). The audit shows Junction's ContextMenuBorderTests with STALE IsSelected and BoundingRect.
    - AT-SPI: true→false sends `state:expanded=0`; false→null sends `state:expanded=0` again and never `expandable` (LinuxAccessibilityBridge.cs:547-549). A caching client keeps "expandable".
    - Suite note: `a11y/progress bar ticks…` reads 0.0 KB/op because its 120 frames make 8 range patches (one per 250 ms) at about 0.1 KB each, with 0 trees. The ledger's "never reaches the refresh" explanation is wrong; the row just cannot show the patch's cost. It could report patches per second as its figure.
  - **Expected:** correctness. Cost while a reader listens:
    - a context-menu move becomes a 2-node patch;
    - a palette keystroke rebuilds only the overlay's subtree (about 30 nodes, about 3 KB), or about 80 KB if the whole ~930-node tree is rebuilt.
  - **Cost:** small–medium. No API change and no pixel change: overlay layout runs earlier in the same frame. It adds events for changes that were silent (see Needs the user).

- **id: a11y-layout-refresh-in-place** (churn and scaling; replaces a11y-layout-refresh-bounds-only)
  - **What:**
    - When a refresh comes from layout (no structure or unpatchable property pending), walk the elements against the applied tree by the builder's rules, instead of rebuilding.
    - Update in place: offscreen bits, scroll offsets, and moved rects (a leaf node is replaced as the leaf patch does).
    - Nodes keep scroll-space rects, and `BoundingRect` is computed from the parent chain (same value as today). A pure scroll then writes one offset plus the offscreen bits.
    - The selection, text and leaf patches then run as they do between refreshes.
    - Any id or count mismatch falls back to the rebuild.
  - **Evidence (Release probe, per step; bridge off / tree only / UIA / AT-SPI, in KB):**

    | Scenario | Off | Tree | UIA | AT-SPI | Trees | What the diff tells |
    |---|---|---|---|---|---|---|
    | Reader-pace walk: 1,000 item rows beside a 55-node details pane, 500 ms keys, scrolls | 7.2 | 98.4 | 99.2 | 399.7 | 1 per key | 2 IsSelected + 1 ScrollPosition |
    | Same walk, no scroll | 4.0 | 95.2 | — | — | 1 per key | 2 IsSelected (the remade rows mark layout) |
    | Wheel over 1,000 rows | 0.1 | 43.2 | 43.2 | 171.9 | 20 per 120 notches | only ScrollPosition; AT-SPI applies 772 KB per refresh and sends 0 signals |
    | Ticking elapsed label (Reel) beside 300 rows, 1 s | 1.1 | 79.3 | 79.7 | 309.8 | 1 per tick | Name only; a fixed-width label is the same |
    | Label edit in 1,000 rows, 500 ms | 1.1 | 173.6 | 174.1 | 691.3 | 1 per edit | 1 BoundingRect + 1 Name |

    - In the reader-pace walk, the 1,000 item rects move on screen with the scroll but 0 move in scroll space, and 2 offscreen states flip.
    - **Junction History** (real app, 61-commit fixture, headless): 500 ms keys cost 78.6 KB/key with a11y off and 92.1 with it on. That is 30 trees per 30 keys; all 30 applies were property-only (IsSelected 60, ScrollPosition 24), with 0 patches. At 60 ms keys: 15 trees per 30 keys. Round 4's real-repo figure: 113 KB a11y per key, 30 %.

      - `virtual/selection walk 1,000 item rows` 25.5 KB vs `a11y/…, bridge on` 112.4 (a11y 77 %);
      - one-argument list 96.6 vs 345.3 (UIA 345.6, a11y 72 %);
      - `a11y/…keys 500 ms apart` 219.1 / 219.5;
      - `a11y/wheel 1,000 rows, UIA` 259.9;
      - `a11y/edit 1 label of 1,000 rows, UIA` 35.8.
    - **Prototype walk** (builder's rules, elements against the applied tree): structure matched every time where it should and allocated 0 B.

      | Scenario | Structure matched | On-screen rect moves | Scroll-space moves | Offscreen flips | Scroll offsets |
      |---|---|---|---|---|---|
      | Reader-pace walk | 40/40 | 1,000 | 0 | 2 | 1 |
      | Wheel | 60/60 | 3,000 | 0 | 8.2 | 1 |
      | Ticking label | 30/30 | 0 | 0 | 0 | 0 |
      | Label edit | 30/30 | 1 | 1 | 0 | 0 |
      | Control: a row added | 0/10 (falls back, correct) | — | — | — | — |

    - **What rides on layout refreshes today** (staleness audit), which the walk must keep telling:
      - composite VirtualList rows realized at render (Aperture grid: Added/Removed Button, Image and Label, ~4,300–10,000 each across the Aperture tests);
      - item-count changes (Junction Tags filter);
      - item label changes (`VirtualListItemRowTests.InvalidateRow`, Junction `RefRowKeepTests`);
      - a click handler added to a live box (`MiddleClickAutoScrollTests`: Box becomes Button).

      The first, second and fourth are id or count mismatches, so they fall back to a rebuild. Item labels need a compare for item-source nodes (cheap for item rows, whose labels are kept) or a fallback when a list's items change.
  - **Expected:** one whole tree per key or tick removed where structure is unchanged.
    - item-row walk 112.4 → ~26 KB/op (−77 %);
    - one-argument walk 345 → ~97 (−72 %);
    - wheel UIA 259.9 → ~1 (−99 %);
    - edit 1 label UIA 35.8 → ~2;
    - the reader-pace walk beside details drops one tree per key (about 53–91 KB of 219, −25…−40 %);
    - Reel playback 1 tree/s → 0 (−79 KB/s UIA, −310 KB/s AT-SPI at 904 nodes);
    - Junction History at reader pace −15 % per key (fixture), −30 % (round 4's real repo).

    Bars: churn on 5+ rows; scaling from O(nodes) allocated per refresh to O(changed).
  - **Cost:** large.
    - The walk must reproduce the builder's rules exactly: flattening, name from content, item and content sources, sticky, overlays.
    - Rects move to scroll space, with `BoundingRect` computed (same public value).
    - AT-SPI geometry has to follow, either read from the node or set in place; this ties to candidate 4.
    - Thread safety: offsets and rects must be swapped whole.
    - No API change; events identical (same diff entries).

    - 3,000 items: the AT-SPI list object has ChildCount 0, and only 2 objects are published. 40 moves are told 0 times on both bridges. For comparison, 1,500 items get 80 UIA IsSelected and 80 AT-SPI selected for the same moves.

  - **Expected:** correctness; no per-item cost.
  - **Cost:** medium; no API change.

- **id: a11y-atspi-snapshot-per-diff + apps-scenario-atspi-rows** (Linux; churn)
  - **What:** keep AT-SPI objects by path across applies, point each at its node on every apply (as UIA wrappers have done since 4195da4), and read geometry and states from the node. Make new objects only for added nodes, and reuse child-path arrays when the child ids are unchanged. Since e2fafa31 the objects' patched fields are already settable.
  - **Evidence:**

  - **Expected:** AT-SPI apply −95…−99 %. After candidate 2, the remaining applies are the structural ones.
  - **Cost:** medium–large; Linux only; no API change.
