CANDIDATES:
- id: a11y-selected-button-patch
  what: mark a selected state in place for a Button that says selected or not before and after, as ea42f45b does for a
  ListItem, so a Meridian map click with a reader no longer builds the whole window's tree.
  evidence:
  - The map's rows are Buttons. The click hands back kept rows, and the reconciler patches the two rows'
    `AccessibleSelected` on the same elements. The observer (Window.cs:4711) sends that change to `_a11yPropertyDirty`,
    so every click builds a tree.
  - KB a click (off / tree / UIA / AT-SPI), JIT, two alternations, identical both times, base → prototype:

    | Endpoints (tree nodes) | Base | Prototype |
    |---|---|---|
    | 60 (253) | 58.1 / 92.3 / 92.7 / 92.8 | 58.1 / 58.3 / 58.4 / 58.6 |
    | 600 (1,873) | 81.5 / 343.6 / 343.9 / 344.1 | 81.5 / 81.8 / 81.8 / 82.0 |
    | 2,000 (6,073) | 120.8 / 973.5 / 973.9 / 974.0 | 120.8 / 121.0 / 121.1 / 121.3 |

  - Trees a click go 1 → 0. The base's "off" matches step 11's 124 KB at 2,000, so with a reader that step's −99 % was
    undone (×8.1 a click).
  - The prototype (`element.Role is ListItem or Button` in that clause) tells a reader exactly the same: IsSelected ×2
    and Name ×2 a click; UIA p:Name 40 and p:IsSelected 40; AT-SPI 83 signals of the same kinds. Stale checks are 0 of
    20 both ways.
  - In every other probe scenario (Vesper 64, Aperture 16, Meridian 21) trees, applies and events are identical.
  - Tests with the prototype: Headless `A11y*` 311 pass and 2 fail. The 2 are `A11yLeafPatchTests` "selected, not an
    item" (UIA and AT-SPI), which pin today's rule. Meridian's 653 pass.
  expected: churn bar: −37 / −76 / −88 % a click with a reader at 60 / 600 / 2,000 endpoints. Scaling bar: it removes
  an O(window) tree build per click.
  cost: small. No API, no pixel or reader change. The only producers of a Button with `AccessibleSelected` are
  Meridian's map and one PerfSuite row; tabs keep their path. An app-only fix (map rows as `ListItem`) would change
  what a reader hears ("button" → "list item"), so it would be the user's call; the framework form is not.

- id: a11y-container-name-in-place
  what: take a node-with-children's own Name or Description change in place, so a Vesper navigation with a reader no
  longer builds the whole tree.
  evidence:
  - Since b4dc84b4 the pane is a Group named after its folder, and the user kept that name (question 24). On a
    navigation the observer (Window.cs:4672: leaves only) sets `_a11yPropertyDirty`, and the walk fails on "a node with
    children changed" (AccessibilityTreeBuilder.Refresh.cs:237).
  - The bound for the fix is a prototype with the pane name held constant (`apply-constname.py`). Trees per navigation
    go 1 → 0, adds and removes are the same, and stale checks are 0 of 10 both ways.
  - KB a navigation (Enter into a 5-file folder, Backspace out), tree / UIA / AT-SPI, base → constant name:

    | View, files | Base | Constant name | Change |
    |---|---|---|---|
    | Detail, 1,000 | 453.2 / 541.4 / 674.8 | 322.4 / 410.7 / 544.0 | −29 / −24 / −19 % |
    | Brief, 1,000 | 453.2 / 492.6 / 538.0 | 336.0 / 375.4 / 420.7 | −26 / −24 / −22 % |
    | Brief, 60 | 231.0 / 249.6 / 269.6 | 204.1 / 222.7 / 242.7 | −12 / −11 / −10 % |
    | Detail, 60 | 221.0 / 226.5 / 234.9 | 201.1 / 206.5 / 214.9 | −9 % |
    | Thumbnails, 60 | 276.1 / 293.9 / 313.1 | 249.7 / 267.5 / 286.6 | −10 / −9 / −8 % |

  - Bytes without a reader are unchanged (Detail 1,000 files: 192.1 KB).
  - The tree the rename builds costs about 20–27 KB at 60 files and 117–131 KB at 1,000 files (2,105 and 1,514 nodes):
    it grows with the window's tree.
  - The same cause accounts for 60 of Junction's 61 audit fallbacks (its Commit button's count, round 8) and 9 of
    Vesper's 10.
  - Round 8 examined this lead at ≤4.5 % of a Junction stage. Two things are new: Vesper's renamed pane, and the growth

  expected: churn bar on Vesper navigation with a reader: −19…−29 % at 1,000 files, −10…−12 % in Brief at 60. Scaling

  ElementId (UIA `UpdateFrom`, AT-SPI `Refresh`). The observer has to send a container's Name or Description change to
  the walk. No API, no reader change.

- id: a11y-focus-find-down
  what: a focus move finds the old and new focused nodes by walking the whole applied tree (`FindNodes`, Window.cs:1318;
  called from `MoveA11yFocus`, :864). Use `FindNodeDown` (Window.cs:1046, which patches already use), keeping the
  whole-tree walk as a fallback.
  evidence: node visits per focus move, counted in the probe by repeating the same walk on the applied tree, against
  the path lookup's depth and children scanned (all 0 B):

  | Scenario | Tree nodes | Whole-tree walk visits | Path lookup |
  |---|---|---|---|
  | Meridian Tab, map with 2,000 endpoints | 6,073 | 6,072 | depth 3, 55 scanned |
  | Meridian Tab, map with 60 endpoints | 253 | 252 | 55 scanned |
  | Vesper Tab | | 118–233 | 23 scanned |
  | Aperture cursor keys | | 56–115 | 49–76 scanned |

  - In Meridian the focused controls come after the map in tree order, so the walk visits nearly the whole tree.
    Aperture's small tree gains nothing.
  - `NotifyPendingA11yFocus` and `Announce`'s `FindA11yNode` walk the whole tree the same way.
  expected: scaling bar only. Each focus move with a reader goes from O(n) to O(depth × siblings), about −99 % of visits
  at 6,000 nodes. Not timed (this is a survey).
  cost: small. Keep the node last marked focused by reference (reset when a build replaces the tree) or find it down
  from its element; keep the whole-tree walk as the fallback. No behaviour change.
