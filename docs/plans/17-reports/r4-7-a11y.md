## Candidates

- **a11y-text-caret-patch.** A caret or selection move in a node with a versioned text source (the
  rich text editor) is marked on the applied tree and handed to the bridges as a patch, with no tree
  built (as list selection since 40b1e97); AT-SPI takes the caret offset from the version.
  RichTextEditorElement.cs:229 notifies TextSelection whenever AccessibilityClients.Active (always on
  this desk), so each arrow key builds and diffs the whole tree. Right/Left keys, 20-block editor beside
  300 rows (903 nodes): bridge off 0.4 KB/key; recording 78.6, UIA 79.0, AT-SPI 319.1 KB/key; 40 trees
  per 40 keys. 5,000-block editor alone: UIA 1.5, AT-SPI 474.9 KB/key (LinuxAccessibilityBridge.cs:473
  reads change.Node.Text for the caret, making the whole text per move). Scaling O(nodes) → O(1);
  beside 300 rows UIA 79.0 → ~0.5 KB/key (−99 %), AT-SPI 319.1 → ~1; 5,000 blocks AT-SPI 474.9 → ~1.
  New suite row (caret walk in rich text, bridge on and UIA). Small–medium; internal
  AccessibleTextVersion gains caret/selection offsets; events identical. Must land before
  a11y-textarea-text-pattern.
- **a11y-text-caret-shares-text.** When only the caret or selection moved (same document, width, layout
  stamp, read-only, scroll), the next text version reuses the previous version's text, line, paragraph
  and geometry tables, replacing only offsets. With a reading client, each caret move re-makes the
  text from layout (TakeTextVersion, RichTextEditorElement.Accessibility.cs:107-111 →
  BuildAccessibleText :265-341): 5,000-block document UIA 474.5, AT-SPI 475.0 KB per caret move (vs 1.5
  with nobody reading) → ~2 KB (−99 %). Small; internal constructor sharing arrays; caret moves only —
  not the keystroke rework the user put off.
- **button-isenabled-rebuild** (approved 2026-10-13). ButtonElement.IsEnabled (ButtonElement.cs:86-96)
  marks style only. Through a component rebuild it is told today only because Button is not opted into
  PatchMarksOwnLayout (its patch marks layout; the refresh carries it); set directly on the live element
  (a Ref write — the pattern plan 17 moved apps to) it is never told (0 trees, 0 diffs over 30 frames;
  a fresh tree differs). componenthost-patch-keeps-layout would silence the rebuild case too. Notify
  on change; both bridges already map it (UIA IsEnabled; AT-SPI enabled, sensitive). Correctness. Small.
- **atspi-reorder-signal** (approved 2026-10-13). For each parent in diff.Reordered, one
  children-changed:add per child whose place in the client's cached order differs, in index order (the
  cached order = previous snapshot's ChildPaths minus removed objects), merged with the added-child
  signals. Live WSL: at HEAD all 7 reorder cases leave a wrong cached order (reverse, swap, rotate,
  last-to-front, reverse+insert, reverse+remove, reverse+append); with the prototype all 17 insert and
  reorder cases match. Signals: reverse of 3 = 2, swap 1, rotate 2, last-to-front 1, reverse+insert 3.
  UIA already raises ChildrenReordered. At most children − 1 extra signals per reordered parent.
  Small. Prototype `r4a11y/reorder-proto.diff`; logs `live/live-baseline.log`, `live-proto.log`.
- **a11y-atspi-snapshot-per-diff** (+ **apps-scenario-atspi-rows** first). AT-SPI objects keyed by
  ElementId and pointed at the current node after every apply (as UIA wrappers since 4195da4); path
  cached; new objects only for added nodes. Every apply costs 271 B per node (paths 88, objects 144,
  child-path arrays 8, dictionary 31):

- **a11y-leaf-property-patch** (first slice of a11y-property-patch). On a frame that would rebuild
  only for property changes of notified leaf elements, make that one node again, compare with the
  applied node, swap it into its parent and hand the bridges a patch: a TextInput's value, a toggle, a
  range, a leaf's name/description/expanded when no ancestor takes its name from content; anything
  else rebuilds. TextInput keystroke: recording 55.5 / UIA 60.7 / AT-SPI 214.5 KB vs 3.2 off
  (TextInputElement.cs:38-42 marks paint only); checkbox click 86.7/87.3/352.2 vs 0.4 off
  (CheckboxElement.cs:23-24); progress ticks rebuild a 3,004-node tree each 250 ms refresh; build+diff
  are 94–99.5 % of the a11y step. Suite: "a11y/type in TextInput, UIA" 53 → ~3–4 KB/op (−93 %);
  "a11y/click checkbox in 500 rows, UIA" 87 → ~1 (−99 %). Scaling O(nodes) → O(depth). Medium; no API
  change; AT-SPI object fields settable for patched properties; label edits that move layout keep the
  coalesced refresh.
- **a11y-textarea-text-pattern** (approved rule). TextArea offers a versioned text source; a
  keystroke is told as a text change, never as a whole-text Value. A 2,000-line keystroke raises a
  121,744-character UIA ValueValue (243 KB BSTR) and an AT-SPI accessible-value of the same length
  (TextAreaElement.cs:117, :1632; LinuxAccessibilityBridge.cs:426-430); caret moves tell nothing today
  (0 trees, 0.5 KB per arrow key). O(text) → O(1) payload per keystroke (UIA TextChanged, AT-SPI
  text-changed with the inserted character). Must follow a11y-text-caret-patch (else each arrow key
  gains a whole tree, +79 KB/key beside 300 rows). Medium (TextArea geometry for the text pattern).
- **a11y-virtual-items-and-selection** (added events approved). AT-SPI serves the items of lists over
  2,000 on demand; the container node carries its selected index, so a move raises UIA IsSelected on
  the UiaVirtualItem and AT-SPI state-changed:selected. 3,000 items: AT-SPI ChildCount 0, 40 moves told
  0 times on both bridges (1,500 items: 80 IsSelected + 80 state-changed:selected); an item-row list
  over 2,000 still rebuilds a 2-node tree 7 times per 40 moves from layout dirt. Correctness; no
  per-item cost. Medium; do it with the next candidate (the container node carries the item source).
- **a11y-uia-host-reads-off-thread.** UIA reads answer from the node (value, toggle, range, an eager
  item's selected state, the list's selection); the container node carries what on-demand reads need;
  fold in the Linux status fix (subscribe to org.a11y.Status first, then the first read through
  AtSpiStatusReader). Every UiaHostBridge read starts with Window.FindElement on the UIA thread
  (UiaHostBridge.cs:249, Window.cs:634-652): 1,505-element page, last checkbox's toggle 1,502 visits,
  a TextInput value 1,504, a slider range 1,505, a gone id walks everything; unsynchronized with the UI
  thread (an exception answers a default); RangeValue pattern reads live (UiaPatternProviders.cs:252)
  while the property reads the node (UiaFragment.cs:232), so they disagree inside the 250 ms
  coalescing; RaiseScrolled walks the live tree on the UI thread per scroll refresh
  (WindowsAccessibilityBridge.cs:685); Linux reads status (LinuxAccessibilityBridge.cs:132) before the
  watcher subscribes (AtSpiBus.cs:207). Scaling O(elements) → O(1) per UIA read; thread safety;
  pattern and property agree. Small–medium; IUiaHostBridge is public, its read members stay (unused).

## Examined, not worth it

- Item-row list moves without a scroll still rebuild the tree every 100 ms with a reader (60 ms keys:
  30 trees per 60 keys; recording 47.4 KB/key, AT-SPI 196.3, vs 4.0 off). Layout dirt from
  VirtualListElement.DropGathered (:480) and every patch (VirtualList not opted into
  PatchMarksOwnLayout, Element.cs:1451, though its rows are laid out in render). Scrolling walks need
  the refresh anyway (suite real-loop row 0.6 trees per key). **Lead for expert 1**: VirtualList patch
  keeps layout; a selection-only drop marks paint; then in-place item changes must tell themselves.
- Text input caret moves (TextInput, TextArea): 0 trees, 0.3–0.5 KB per key.
- Reorder signal cost: O(moved children) per reordered parent; no cheaper order satisfies libatspi.
- UIA apply 5.2 KB on the TextInput row: the probe's own Wrappers LINQ snapshot; real apply 0.3–0.5 KB.
