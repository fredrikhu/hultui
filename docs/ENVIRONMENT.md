# Environment Variables and Build Switches

Every knob the framework, the apps and the tests read from the environment, in one
place. The Value column is what the code tests for, exactly. An on switch (`1`) acts only on
`1`, and an off switch (`0`) only on `0`; any other value, `true` and `false` included, is the
same as leaving the variable unset. The few that ignore case or accept more say so in the row.

## Framework

| Variable | Value | Effect |
|---|---|---|
| `HULTUI_A11Y` | `0` | No accessibility bridge is created for any window, on any platform. Read once per window at construction. The purpose is equalising benchmarks against a machine with no assistive technology attached (on Linux the AT-SPI bridge otherwise connects whenever a bus is reachable), and an escape hatch if a bridge misbehaves. Any other value leaves it on. |
| `HULTUI_UIA_EVENTS` | `0` | Windows only, finer than the above: the UIA tree stays exported but no structure, property or focus-changed events are raised. |
| `HULTUI_TRACE` | a file path | Starts frame-trace recording at window creation and writes the trace there when the window is disposed. F11 still toggles a trace by hand and takes precedence. |
| `HULTUI_STARTUP` | `1`, or a file path | Phase timings from process launch to the first presented frame (`SDL_Init`, `SDL_CreateWindow`, GL context, Skia surface, first frame). `1` prints to stderr; any other value is taken as a file to write. Needs no app change: the marks are in the framework. |
| `HULTUI_GL_PRELOAD` | `1` | Lets `Application.BeginGraphicsPreload()` do something. With it set, an app that calls that method as the first statement of `Main` loads the GL driver on a worker thread and warms the text pipeline while its own pre-window work runs. Opt-in because loading the driver off the main thread is outside SDL's documented threading contract; validated on Windows/WGL, not on X11/Wayland. Without the variable the call is a no-op. The load stays on the critical path, so what is saved is only the main-thread work the app does anyway, plus the text pipeline's warm-up: ~10 ms measured on Junction, ~25-30 ms on Reel (Release JIT, five runs each way, first frame 502 ms without and 473 ms with, no run overlapping). Reel sets this itself on Windows when nothing else has, so its installed build gets it by default; setting it to `0` still turns it off. |
| `HULTUI_RENDERER` | `vulkan` (any case) or `gl` | **An override; apps choose in code with `new Application(..., renderer: RendererKind.Vulkan)`**, which Reel and Aperture do. `vulkan` in any case turns Vulkan on for an app that never asked. Any other non-empty value (`gl` by convention) turns it off for one that did. Empty or blank means unset and leaves the app's own choice, which is GL unless the app asked for Vulkan. It wins over the app because it is how every command in the design docs selects a renderer, and how a machine where Vulkan misbehaves is got working again without a rebuild. For the same reason, when it forces Vulkan and Vulkan cannot start, the app fails instead of falling back; an app's own request falls back to GL with a line on stderr. Read when each window is created. Vulkan is the only renderer here that can present HDR. On an HDR display it picks the scRGB half-float swapchain, and elsewhere 8-bit sRGB (`HULTUI_VULKAN_F16` overrides). It presents with MAILBOX where the surface offers it, then IMMEDIATE, then FIFO (`HULTUI_VULKAN_PRESENT` overrides). What each choice costs is measured in `docs/design/HDR.md`. |
| `HULTUI_VULKAN_CAPTURE` | a file path | Writes one presented swapchain image there as a PPM, then carries on. The only way to see what this renderer actually drew: the headless driver renders through `SkiaRasterRenderSurface` and never touches a GPU backend, and screen-grabbing the window captures whatever is in front of it. Diagnostic — it stalls the queue and allocates a staging buffer. Captures the **first frame that reuses a swapchain image**, not the first frame drawn: while every image is still fresh every belief about it is true, and a renderer can draw those frames perfectly and every frame after black. `HULTUI_VULKAN_CAPTURE_FRAME` picks another. The count restarts whenever a swapchain is built, so the file always holds the newest swapchain's work — resize the window and what lands on disk is from the size it is now, which is how a resize gets checked without looking at the screen. |
| `HULTUI_VULKAN_CAPTURE_FRAME` | a positive integer | Which presented frame of each swapchain `HULTUI_VULKAN_CAPTURE` writes, counting from 1. The default is one past the swapchain's image count. A window that only draws when something changes may never reach a large number, so a capture that never appears can mean an idle window rather than a renderer that drew nothing. |
| `HULTUI_VULKAN_INTEROP` | `0` | Refuses the shared Vulkan/OpenGL image and leaves video on the software path — phase 4 of `docs/design/HDR.md`. Only meaningful on the Vulkan renderer, where a video is otherwise decoded by mpv into a GL framebuffer over an image the Vulkan device owns, with no copy through main memory and sixteen bits a channel instead of eight. There to be turned off: the arrangement leans on two drivers agreeing about one allocation, and a machine where that goes wrong should still be able to play something. It is also how the two paths are compared on one clip. The interop is refused automatically, with a line on stderr, when the driver lacks the external-memory extensions or the GL context lands on a different GPU than the Vulkan device — so this is an override for the case where it is available and still wrong. Nothing is created until the first frame that draws a video; a window that never shows one pays nothing. |
| `HULTUI_VULKAN_SEMAPHORE` | `0` | **Off switch.** By default GL and Vulkan are ordered over the shared image with a semaphore exported from the device and imported into the GL context, so nothing blocks the CPU. Setting this to `0` goes back to `glFinish` and a queue wait, which is correct and costs: on a 4K HDR decode the renderer uses 62 ms of CPU a second with the semaphore and 156 without, against 56 for the GL renderer. `HULTUI_VULKAN_FINISH_TRACE` prints the per-frame split. |
| `HULTUI_VULKAN_FINISH_TRACE` | `1` | Prints to stderr, every 120 frames that drew video, what ordering the shared image cost per frame: the `glFinish` or semaphore signal, and the barrier submit, with the CPU a second that comes to at 24 fps. Diagnostic. |
| `HULTUI_VIDEO_HDR` | `0` | **Off switch.** By default a video producer is asked for linear light with its HDR range intact rather than a tone-mapped SDR picture — phase 5 of `docs/design/HDR.md`. On by default because the alternative is incoherent: a renderer that picked an HDR swapchain and then asked the decoder to throw the range away has wasted the swapchain. Only ever asked on an scRGB swapchain, so an SDR display is untouched, and a producer that does not understand the request keeps writing encoded pixels and says so. Measured on a film mastered at 1000 nits, with mpv told a 1000-nit peak: the shared image's maximum goes from 1.0 to 4.926, which is 1000/203, the mastering peak intact. Drawn at 203/240 of the canvas and blitted at the SDR white of 3.0, that is 12.5 in the swapchain, which is 1000 nits. Told the test panel's own 455-nit peak, mpv tone-maps the highlight to 455 instead (2.240 × 203). Set to `0` for a driver that mishandles it. |
| `HULTUI_VIDEO_WIDE_GAMUT` | `0` | **Off switch.** On an scRGB (HDR) Vulkan window, video keeps colours outside BT.709 as negative channel values, which scRGB shows as the colours they are, instead of desaturating them into BT.709 first: mpv gets `gamut-mapping-mode=clip`, which in its GL renderer skips the mapping rather than clamping. Measured on BT.2020 colour bars: the green bar reaches the shared image as (-0.26, 0.50, -0.04), the BT.2020→709 matrix exactly, and not as (0, 0.41, 0.12), pulled toward cyan. Grey and an in-gamut green come out the same either way. The negatives reach the swapchain on every path, including the gamma-2.2 one, whose encode and decode keep the sign. `0` goes back to mapping inside BT.709. |
| `HULTUI_VIDEO_HDR_PROBE` | a frame count | Reads the shared image back through GL every n frames, six times, and prints what the producer actually wrote into it. Diagnostic: the read is the whole image and stalls. It exists because the swapchain report is taken after compositing, so a missing range there does not say whether the producer or the renderer lost it — and because the equivalent read through Vulkan needs a layout Skia owns and moves. Take more than one sample: a black frame reads exactly like a producer writing nothing. |
| `HULTUI_VIDEO_WHITE` | `ui` (any case) | Where a video's reference white is put when `HULTUI_VIDEO_HDR` is on. The default puts it at the 203 nits it actually names, so the picture is absolutely correct and the interface around it — drawn at the display's SDR white, 240 nits here — is 18% brighter than white in the film. `ui` stretches the video so the two match instead, and every absolute luminance in the film is then wrong by that factor. **Decided by looking, 2026-09-28: `reference` stays the default.** The bar does read visibly hotter than the film's whites without `ui` — the 18% is not theoretical — but a correct picture beats matching chrome, since the film's absolute luminances are the point of the HDR work. **On Wayland this setting does nothing**: the protocol's scRGB white is 2.5375, and 2.5375 x 80 = 203 nits, which is already libplacebo's reference white, so the scale computes to 1. It only bites where the display's SDR white differs from 203. |
| `HULTUI_VULKAN_PEAK_NITS` | a positive number | Overrides the display's peak luminance, which is used for tone mapping. mpv accepts 10 to 10000 nits, so a value outside that is clamped to it. It is **queried** rather than assumed. With display-colour events on (`HULTUI_DISPLAY_INFORMATION`, Windows 11 22H2 and later) it comes from Windows' own `DisplayInformation` as an absolute luminance (455 nits on the test machine, where the old assumed 1000 had mpv tone-mapping to more than twice what the panel can show). Elsewhere it is SDL's HDR headroom times SDR white — on Windows SDL's own white, because headroom is relative to it and the two are one snapshot; on Wayland the 203-nit protocol reference. Set this only to override a display that reports wrongly. |
| `HULTUI_DISPLAY_INFORMATION` | `1` or `0` | Windows 11 22H2 and later: whether a Vulkan window follows display-colour changes by event — WinRT's `DisplayInformation.AdvancedColorInfoChanged` — so that switching HDR or dragging the SDR brightness slider reaches it at once. **Off by default**; apps turn it on with `new Application(..., displayColorEvents: true)`, which Reel and Aperture do, and this overrides the app either way (`1` on, `0` off). Without it the window polls the display configuration every 100 ms, which is correct and trails a dragged slider slightly — the slider sends no window message at all, so nothing SDL sees can announce it. The event is hand-rolled COM hooked into the window's message loop, which is why it is opt-in. Start-up cost when on: about 9 ms. |
| `HULTUI_SDR_TRANSFER` | `srgb` or `2.2` (any case) | How an scRGB (HDR) Vulkan window turns its sRGB colours into light. Default: `2.2` under Wayland, `srgb` (the piecewise curve Skia uses) elsewhere. KWin shows an ordinary sRGB window through a pure 2.2 gamma, and with the piecewise curve the Vulkan window's shadows came out lighter and greyer than a GL window beside it — the navy UI and a film's blacks alike, while white matched. In `2.2` the UI is drawn encoded, as on an 8-bit swapchain, and decoded once on the way to the swapchain; linear-light video is encoded with the inverse and comes out unchanged. For comparing the two by eye. |
| `HULTUI_VULKAN_PRESENT` | `immediate`, `mailbox`, `fifo`, `fifo-relaxed` (any case) | Pins the Vulkan present mode. The default is **MAILBOX**, and the reason is a visible defect: on IMMEDIATE a window dragged by its edge stretches its old contents before snapping to a correct frame. Measured by capturing the screen and reading back a bar drawn 300 device pixels wide — it came back 402 on 25 of 174 resizes that grew the window by exactly that ratio, so the compositor was scaling the previous swapchain's image up. GL never did it; MAILBOX and FIFO never did it. There were two causes and this is the second: the first was a live-resize frame that could be skipped and then never drawn, since the SDL event watch is the only code running during the Win32 modal resize loop and nothing comes round again until the drag pauses — that throttle is now gone from that path. IMMEDIATE still stretches about 1 resize frame in 30 afterwards; MAILBOX and GL do not. **The trade-off is real and measured:** MAILBOX keeps video level with GL (54 ms/s against 55) but costs 789–804 ms/s of CPU while a resize is actually in progress, against IMMEDIATE's 275–366 and GL's 90–123 — and that is driver-side, not frames we choose to draw, since halving the resize frames left it unchanged. FIFO is the other way round: 297–390 ms/s through a resize and the cheapest present pass of the three, but 78 ms/s on 4K HDR video against MAILBOX's 54, because it is vsync in the presentation engine and paces the loop from underneath whatever `Application` wanted. Continuous playback lasts longer than a drag, so MAILBOX wins. A mode this surface does not offer is ignored rather than fatal. |
| `HULTUI_VULKAN_ACQUIRE_TRACE` | `1` | Prints to stderr, every 120 frames, what waiting on the swapchain acquire costs per frame. The acquire waits on a fence because SkiaSharp exposes nothing to hand a semaphore to; measured at 0.0064 ms a frame, which is why it stays. Diagnostic. |
| `HULTUI_VULKAN_FIXED_EXTENT` | `1` | Allocates the Vulkan swapchain larger than the window — rounded up to a 256-pixel bucket — and presents it un-scaled, through `VK_KHR_swapchain_maintenance1` with `PRESENT_SCALING_ONE_TO_ONE` and `PRESENT_GRAVITY_MIN`. **Off by default, and video is the reason.** It works: a drag rebuilds the swapchain 10 times instead of 122 and costs 466 ms/s of CPU instead of 801, against GL's 264, with validation clean and no measurable change in working set, private bytes or handles. It also removes the resize stretch *structurally* rather than by racing — with nothing for the compositor to scale, even IMMEDIATE goes from 18 stretched frames in 150 to 0. But it costs 4K HDR playback about 70% more CPU (91–95 ms/s against 48–63, three reps with GL alongside as a drift reference), because a swapchain whose extent matches the window can be handed to the compositor directly and one that does not appears to be copied instead. Video runs for hours and a drag lasts a second, so the default favours video. Turning it on only during a drag would get both and needs a settled-size signal the renderer does not have. Requires `VK_KHR_get_surface_capabilities2` plus `surface_maintenance1` on the instance and the device extension with its feature bit; without any of them, or without ONE_TO_ONE and MIN gravity on the surface, it is ignored and the swapchain is rebuilt per resize as before. |
| `HULTUI_VULKAN_SCALED_SPACE` | `1` | Carries the display's SDR white scale in the destination colour space instead of the scRGB offscreen pass — the render target is declared `linear = stored / k`, so Skia stores `k` where it wanted 1.0 and nothing has to multiply the frame afterwards. **Opt-in.** It works and the output is identical: a capture of the presented swapchain differs from the offscreen path in 0 of 5,335,200 channels, the present pass goes from 0.40 ms to 0.30, video is unaffected, and it deletes a full-screen F16 surface, an SkSL colour filter and a blit. But the memory saving does not appear — dropping the offscreen for a *plain* linear space frees about 17 MB across two windows, dropping it for this one frees nothing, reproducibly. Skia spends about what the offscreen cost on a transfer function it does not recognise. So the trade is 0.10 ms a frame for no memory, on a path off Skia's usual one, which is worth having and not worth defaulting to. Ignored unless the swapchain is scRGB, the white scale exceeds 1, and the display is not reported as gamma 2.2 (KWin is, and keeps the offscreen). Untested on Linux. |
| `HULTUI_VULKAN_F16` | `1` or `0` | Asks for the half-float linear (scRGB) swapchain instead of 8-bit sRGB — phase 2 of `docs/design/HDR.md`, and what phase 3 presents HDR through. Requires `VK_EXT_swapchain_colorspace`, which the host then enables. **Not off by default any more** — phase 3 made the display decide, and this is an override in both directions (`0` forces 8-bit sRGB on an HDR display). `HULTUI_VULKAN_WHITE_SCALE` overrides the display's reported SDR white level. Appearance is meant to be unchanged: measured against the 8-bit path, 99.0% of channels identical and 296 of the 297 differing pixels sit on an antialiased edge, where linear-light blending genuinely differs and is the more correct of the two. Costs roughly half the frame rate on an RTX 4080 (9187 → 4150 fps unpaced), which is the bandwidth of a 64-bit target. |
| `HULTUI_VULKAN_WHITE_SCALE` | a positive number | The SDR white of an scRGB window in scRGB units (1.0 = 80 nits; 3.0 is 240 nits), winning over every display source. For a machine where the query fails, for comparing by eye, and for telling the cost of the white-scale pass from the cost of the half-float target, since 1 turns the pass off. |

## Media (`HultUI.Media.Mpv`)

| Variable | Value | Effect |
|---|---|---|
| `HULTUI_MPV_PATH` | a file or a directory | First place the libmpv resolver looks: a path to the library itself, or a directory to search for `libmpv-2.dll` / `libmpv.so.2` / `libmpv.2.dylib`. After that: the application directory, `runtimes/<rid>/native` beneath it, then the loader's own search. |
| `HULTUI_MPV_HWDEC` | an mpv hwdec mode | Overrides `hwdec`, which defaults to `auto-safe` (zero-copy where the libmpv has the interop, a `-copy` mode otherwise; the same as `auto` on mpv 0.40 and later, and safer on an older distribution libmpv, where `auto` skips the whitelist). On Windows the bundled libmpv now has NVDEC with CUDA interop, so on NVIDIA `auto` gives true zero-copy through `nvdec` — confirmed by the VO line reading `cuda[p010]` rather than `p010`, on both renderers. The DirectX interops stay disabled (`d3d11va` and `dxva2` would bridge at 8 bits), so a non-NVIDIA machine lands on `d3d11va-copy` as before. `no` forces software, which is how the decoder's share of the CPU was measured: 468 ms/s with hardware decoding and 921 without, on 4K HEVC. `HULTUI_STARTUP` prints what mpv actually chose, which is worth reading — a silent fallback looks exactly like the mode working, because the fallback also decodes on the GPU. On Linux the trimmed build has NVDEC with CUDA interop (NVIDIA driver 530.41 or newer), and so does a distribution libmpv such as RPM Fusion's: there `auto` gives true zero-copy through `nvdec`, about 185–250 ms/s less CPU at 4K than `auto-copy`, which resolves to `nvdec-copy` or `vulkan-copy`. See Decode in `docs/design/HDR.md`, and `docs/design/HDR-LINUX-ZEROCOPY.md` for the Linux measurements. |
| `HULTUI_MPV_LOG` | an mpv log level (`warn`, `info`, `v`, `debug`) | Forwards mpv's own log to stderr at that level. |
| `HULTUI_MPV_OPTIONS` | `name=value;name=value` | Extra mpv options, set before initialisation. Pairs are separated by `;`, and only a pair's first `=` splits, so values may contain their own. It is diagnostic: it is how a test clip is told what it is when its container cannot say. A Y4M of BT.2020 colour bars (`spikes/HdrInterop/make-bars.cs`) needs `vf=format=colormatrix=bt.2020-ncl:primaries=bt.2020:gamma=pq`. A pair mpv refuses is reported on stderr and skipped. |

## Web view (`HultUI.WebView.*`)

| Variable | Value | Effect |
|---|---|---|
| `HULTUI_WEBVIEW2_LOADER` | a file or a directory | Windows: first place `WebView2Loader.dll` is looked for, as the file itself or a directory holding it. After that: beside the application, its `runtimes/<rid>/native`, then the host's own probing. |
| `HULTUI_WEBVIEW2_INTEROP` | `0` | Windows: turns off the in-place GPU path, in which a page's captured frame is read by GL through `WGL_NV_DX_interop2`, and uploads every frame instead, at about 220 ms/s of CPU against 60–100 for an animating page. For a driver that mishandles the interop, as `HULTUI_VULKAN_INTEROP` is for video. |
| `HULTUI_CEF_DIR` | a directory | Linux: the CEF to use, looked for first: a directory holding `libcef.so` with its resources beside it (`icudtl.dat`, the `.pak` files, `locales/`), laid out flat. After it: `cef/` beside the application, its `runtimes/<rid>/native/cef`, then the distribution's (`/usr/lib64/cef` on Fedora, `/usr/lib/cef` on Arch). The engine also sets it, in the native environment, for its helper process. |
| `HULTUI_CEF_HELPER` | a file | Linux: the subprocess executable (`hultui-cef-helper`) to give CEF, looked for first. After it: beside the application, then its `runtimes/<rid>/native`. |
| `HULTUI_CEF_LOG` | `verbose`, `info`, `warning`, `error` or `disable` | Linux: CEF's log level, on standard error. CEF's own default otherwise. With `info` or `verbose` the engine also says what it chose, such as how a page's frames travel (`page frames: zero-copy`, or `read back`, or `pixels`). |
| `HULTUI_CEF_ZERO_COPY` | `0` | Linux: keeps a page's frames on the pixel path under Wayland too. By default, on Wayland, CEF hands each frame over on the GPU and HultUI blits it without a pixel crossing the CPU: about 95–120 ms/s of this process's CPU for an animating page at 1656×968, 60 frames a second, against 170–240 for pixels (GL and Vulkan alike). Under X11 pages are always pixels. For a driver that mishandles the dmabuf hand-over, as `HULTUI_WEBVIEW2_INTEROP` is on Windows. |
| `HULTUI_CEF_SWITCHES` | `name[=value]` separated by spaces | Linux: more Chromium switches for the browser process, after the engine's own. For diagnosis and tests (the engine tests use it for a fake camera and microphone); not a supported way to configure an application. |
| `HULTUI_CEF_API_VERSION` | — | Set by the engine for its helper process, with `HULTUI_CEF_DIR`. Not for setting by hand. |

## App conventions (not read by the framework)

| Variable | Where | Effect |
|---|---|---|
| `HULTUI_DEVTOOLS` | Junction, Vesper Commander, Meridian | `1` sets `app.DevToolsHotkeysEnabled` in a Release build, so a shipped installer can be inspected without rebuilding. The framework property does not read it; each app does. See [DEVTOOLS.md](DEVTOOLS.md). |
| `HULTUI_TRACE_MS` | Junction | An integer: drive continuous frames for that many milliseconds, then close the window so shutdown flushes `HULTUI_TRACE`. |
| `JUNCTION_BENCH` | Junction | A script of interaction steps at absolute milliseconds since launch (`Branches@4000,History@12000,…`), annotated into the trace. |
| `HULTUI_MEDIA_NOHIDE` | the VideoPlayer and ProceduralVideo samples | `1` keeps the transport bar visible, for screenshots under the headless driver, which compresses time so the bar would otherwise auto-hide. |

|---|---|---|

## Build-time defines

These are **MSBuild properties, not environment variables**; they become
`DefineConstants` and change what is compiled in.

| Property / symbol | Default | Effect |
|---|---|---|
| `HultUIStrictLifetime` → `HULTUI_STRICT_LIFETIME` | on in Debug, off in Release | Reading `Layout` or writing a scroll offset on an element that reconciliation discarded throws, naming the element and its build site. Within a strict build `Element.StrictLifetimeChecks` is a runtime switch for a test that means to inspect a discarded element. See [DECISIONS.md — the detached-element trap](DECISIONS.md#the-detached-element-trap). |
| `HultUIElementOrigin` → `HULTUI_ELEMENT_ORIGIN` | on in Debug, off in Release | Records the source file and line each element was built at (`Element.Origin`), which DevTools and the strict-lifetime message show. |

Override either from the command line:

```bash
dotnet build -c Release -p:HultUIStrictLifetime=true
```

## Related application settings

Not environment variables, but the switches people look for alongside them:

- `Application.FramePacing` — `Display` (default: at most one render per display
  interval, events handled as they arrive) or `Unlimited` (render whenever anything is
  dirty, for measuring). Neither touches the swap interval, which stays 0 so a vsync'd
  swap cannot block the Win32 modal resize loop. See [THREADING.md](THREADING.md).
- `Window.RefreshRate` — the display's rate in Hz, 0 when unknown; the loop falls back
  to 60.
- `Application.DevToolsHotkeysEnabled` — the one switch for Ctrl+Shift+I, F12 and F11.
- `UIThread.Enforce` — the wrong-thread guard, on in Debug builds of `HultUI.Core`. See
  [REACTIVITY.md — the thread guard](REACTIVITY.md#the-thread-guard).
