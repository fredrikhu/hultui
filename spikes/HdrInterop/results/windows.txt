Reading it: the cost is flat across resolutions — 0,25 ms at 1080p and 0,25 ms at 4K —
so it is not the image being waited on, it is the fixed price of submitting a command
buffer and waiting for the queue to go idle. That is the crudest possible ordering, and
a renderer that already submits work each frame pays most of that price anyway.

Verdict: the naive sync costs about 4 % of a 24 fps frame budget and replaces a copy
costing 175 ms/s. External semaphores would remove the stall, but they are an
optimisation, not a precondition — phase 4 can be built without them.

--churn, 2026-09-25, RTX 4080, Windows
does one export/import cycle leak a handle?
═══════════════════════════════════════════════════════

  five exports, one allocation:  0x76C 0x76C 0x76C 0x76C 0x76C
  five exports, fresh allocations: 0x77C 0x788 0x768 0x77C 0x788

  1000 cycles, released properly
    handles 494 -> 495   (delta +1)
    0,125 ms a cycle

  200 exports deliberately dropped (the control: handle never closed)
    handles 496 -> 696   (delta +200)

  The control climbed, so this measurement can see a leak.
  VERDICT: 1000 released cycles cost no handles. The cycle does not leak.

Two things had to be got right before the number meant anything, and the first
version of this test got both wrong.

  1. The allocation has to be recreated each cycle. NVIDIA returns the SAME
     Win32 handle for repeated exports of one VkDeviceMemory (0x76C above), so a
     test that exports one allocation a thousand times cannot leak and cannot
     fail. The renderer frees and reallocates on a video size change, which is
     what produces the distinct handles in the second row.

  2. Process.HandleCount is not the number. It comes through a performance
     counter that does not move per handle, and read a flat 492 while 200
     handles were being leaked. GetProcessHandleCount is exact.

Both faults produced a clean-looking pass. The control is what caught them: a
flat line means nothing unless the same measurement can be made to rise.

--range, 2026-09-25, RTX 4080, Windows
can mpv be made to write HDR range into the shared image?
═══════════════════════════════════════════════════════

Three-band clip (limited-range 235 / 126 / 16), rendered into the shared RGBA16F
image, read back. y=90 is the mid-grey band, which is the row that tells an
encoded picture from a linear one; 235 and 16 are limited-range white and black
and come out 1.0 and 0.0 either way.

  options                                    mid-grey    max     over 1.0
  (none — today)                             0,5020      1,0000  none
  target-trc=linear                          0,1921      1,0000  none
    + target-prim=bt.709                     0,1921      1,0000  none
    + target-peak=1000                       0,1921      1,0000  none

So target-trc DOES reach libplacebo through the render API: 0,5020 encoded
becomes 0,1921, which is that value decoded through gamma 2.4. The options are
not ignored. But SDR content has nothing above reference white, so no target
configuration can make it exceed 1.0 — that was the wrong clip to ask with.

Claiming the same clip is PQ BT.2020 on the way in gives it something to carry:

  vf=format=gamma=pq:primaries=bt.2020                   max 1,0000  none
    + target-trc=linear                                  max 1,0000  none
    + target-peak=1000 tone-mapping=clip                 max 4,9258  ALL

  → HDR range does come through the OpenGL render API into the shared image.

target-peak is the gate, and the number it produces is exact:

  target-peak=203   ->  max 1,0000
  target-peak=406   ->  max 2,0000
  target-peak=1015  ->  max 5,0000

**libplacebo's linear output is normalised so that 1.0 is 203 nits** — the
BT.2408 reference white, to four decimal places, not an approximation.

That is the same 203 the Wayland colour-management protocol names as the
reference white of Windows-scRGB, which is why the white scale there is 2.5375 =
203/80. Both ends of this pipeline already agree on the number:

  mpv linear (1.0 = 203 nits)  ->  scRGB (1.0 = 80 nits)   is  x 2.5375

which is exactly the scale SDL3Window.WhiteScale already returns on Wayland.
On Windows the UI's scale comes from the display's own SDR white instead (240
nits here, so 3.0), so UI white and video reference white would sit 240/203 =
18% apart. That gap is the actual subject of phase 5, and it now has a number.

Phase 5 end to end, 2026-09-26, RTX 4080, Windows
2001 (PQ/BT.2020, mastering peak 1000.6 nits), at 20:00
═══════════════════════════════════════════════════════

Two points in the pipeline, same run. The shared image is read through GL inside
RunExternalGL, right after mpv renders; the swapchain is read at capture time,
after Skia has composited.

  HULTUI_VIDEO_HDR=0   shared image max 1,000  ( 0 above 1)
                       swapchain    max 3,000  ( 0 above SDR white of 3,00)

  HULTUI_VIDEO_HDR=1   shared image max 4,926  ( 537856 above 1)
                       swapchain    max 12,281 ( 586929 above SDR white)

4,926 is 1000/203 exactly: the film's mastering peak, arriving intact, measured
against libplacebo's reference white. And 12,281 in scRGB is 12,281 x 80 = 982
nits on screen for a 1000-nit highlight — right to within the frame-to-frame
variation of where the peak falls.

The 0..1 offscreen does NOT clamp. That was the main worry going in, since phase
2 built it on the assumption nothing exceeds white, and 12,281 passed through it.

Three false conclusions on the way here, all the same mistake in different
clothes, all worth more than the result:

  1. "The swapchain clamps HDR."  Measured at frame 60, which is 2,5 s into a
     film that opens on a three-minute black overture. A black frame reports a
     maximum of 0,000 or 1,000 and reads exactly like a producer that tone-mapped
     everything away.

  2. "The producer tone-maps it away."  One probe sample, which landed on black
     again even after seeking. The probe now takes six spaced samples.

  3. "Seeking fixed it."  --start seeked immediately after Open, which is before
     the backend has loaded anything, so the seek was silently dropped and the
     film played from the beginning. It now waits for a known duration.

Every one of those produced a confident number from a frame with nothing in it.
The lesson is not "check the timestamp" — it is that a measurement which cannot
distinguish "nothing was drawn" from "nothing bright was drawn" is not a
measurement, and both readings here look identical.

GL_DEDICATED_MEMORY_OBJECT_EXT on Windows, 2026-09-26
the flag Linux needed, checked on the platform that
worked without it
═══════════════════════════════════════════════════════

Linux found that EXT_external_objects requires the imported memory to be marked
dedicated when Vulkan allocated it that way, and that NVIDIA-Linux returned a
black texture above about 2560x1440 without it — no GL error, complete
framebuffer, every 4K film black. Windows happened to work regardless, so the
flag was added there untested.

It is correct on Windows too. 2001 at 3840x1746, HDR on, after the flag:

  shared image max 4,926 (555196 above 1.0)
  swapchain    max 12,359 against an SDR white of 3,00 (591895 above)

the same numbers as before it, so nothing regressed and the spec-required call
costs nothing here.

are small (320x180) and undefined happened to mean right — but SyncBench imports
