--churn, 2026-09-25, RTX 4080, Windows
does one export/import cycle leak a handle?
═══════════════════════════════════════════════════════

  five exports, one allocation:  0x76C 0x76C 0x76C 0x76C 0x76C
  five exports, fresh allocations: 0x77C 0x788 0x768 0x77C 0x788

  1000 cycles, released properly
    handles 494 -> 495   (delta +1)
    0,125 ms a cycle

  200 exports deliberately dropped (the control: handle never closed)
    handles 496 -> 696   (delta +200)

  The control climbed, so this measurement can see a leak.
  VERDICT: 1000 released cycles cost no handles. The cycle does not leak.

Two things had to be got right before the number meant anything, and the first
version of this test got both wrong.

  1. The allocation has to be recreated each cycle. NVIDIA returns the SAME
     Win32 handle for repeated exports of one VkDeviceMemory (0x76C above), so a
     test that exports one allocation a thousand times cannot leak and cannot
     fail. The renderer frees and reallocates on a video size change, which is
     what produces the distinct handles in the second row.

  2. Process.HandleCount is not the number. It comes through a performance
     counter that does not move per handle, and read a flat 492 while 200
     handles were being leaked. GetProcessHandleCount is exact.

Both faults produced a clean-looking pass. The control is what caught them: a
flat line means nothing unless the same measurement can be made to rise.

MPV_RENDER_PARAM_DEPTH, 2026-09-27, RTX 4080, Windows
was the half-float target being dithered to 8 bits?
═══════════════════════════════════════════════════════

Yes. The backend never passed MPV_RENDER_PARAM_DEPTH, and the render API says an
absent or zero depth means the renderer assumes 8 and dithers to them. The open
question was whether internal_format supersedes it. It does not.

A 10-bit ramp (1024 columns, limited-range 64..940, so 877 source levels) into an
RGBA16F shared image, middle row read back:

  DEPTH omitted   256 distinct levels, 250 direction reversals, mean step 0,00193
  DEPTH = 16      951 distinct levels,  62 reversals,            mean step 0,00100
  DEPTH = 8       256 distinct levels, 250 reversals,            mean step 0,00193

The third row is the control and the one that settles it: forcing 8 gives output
identical to omitting it, so "omitted" really is being treated as 8 rather than
inferred from the target. 256 levels across 1024 pixels with the row reversing
direction 250 times is quantisation plus dither noise, in a surface that holds
sixteen bits a channel.

A ten-bit source is needed to see this at all. An eight-bit clip is already on
the grid being looked for, which is why every earlier measurement here — all of
them on 8-bit synthetic clips or on maxima rather than gradients — missed it.

Fixed by deriving the depth from the target's internal format: 16 for RGBA16F,
32 for RGBA32F, 8 for RGBA8 and anything unrecognised. The sink's own texture is
RGBA8 and still gets 8, so the GL renderer is unchanged.

Confirmed end to end in the app, not just the spike — the same ramp played in
the video player on the Vulkan renderer, shared image read back through GL:

  middle row 882 levels, 22 reversals

which is the source's 877 levels plus a little YUV-to-RGB rounding. The ten bits
now arrive.

Synchronisation, 2026-09-27, RTX 4080, Windows
is the CPU stall the class warned about still there?
═══════════════════════════════════════════════════════

Mostly not, and what is left is not worth replacing.

The expensive half was already gone: the queue drain after Skia submits had been
replaced by a semaphore the present waits on. The class comment still described
the drain, which is how this came to be re-investigated.

SkiaSharp 3.119.2 still cannot be handed a semaphore — no GRFlushInfo, no
GRBackendSemaphore, and the only native entry points its binding carries are
gr_direct_context_flush and gr_direct_context_flush_and_submit, neither taking
flush info. Checked against the assembly rather than assumed.

What the remaining fence costs, 120 frames of continuous animation paced to a
120 Hz display:

  acquire wait: 0,0064 ms a frame

Six microseconds. Replacing it with a semaphore moves six microseconds from the
CPU to the GPU.

Where the Vulkan path does cost more than GL, same benchmark, --auto:

  operation            GL        Vulkan
  create 1,000         28,47     28,73
  update every 10th     2,41      2,66
  select row            0,43      0,59
  swap rows             1,09      1,33
  remove row            6,73      6,89
  create 10,000       316,64    319,84
  append 1,000         38,25     36,78     (Vulkan faster)
  clear 1,000           0,27      0,41

A fixed 0,15 to 0,25 ms a frame, visible only where the frame is small enough for
it to matter and invisible on anything layout-bound. That is consistent with the
two things this backend does that GL does not — one extra command-buffer submit,
and a render target rebuilt every frame because Skia cannot be told a layout —
both the same binding limitation as the semaphore, and neither a stall.

VERDICT: do not build the semaphore acquire. The number says no.

Zero-copy decode, 2026-09-27, RTX 4080, Windows
scoped, and not built — the Windows route is 8-bit
═══════════════════════════════════════════════════════

CPU, 4K HEVC HDR, release build, 20 s window after 12 s settle, Vulkan renderer:

  hwdec=auto-copy (default)   468 ms of CPU per second
  hwdec=auto                  415 ms/s
  hwdec=no (software)         921 ms/s

The middle row is NOT a zero-copy saving. Both auto and auto-copy resolve to
d3d11va-copy on this build, so the 53 ms/s between them is run-to-run variance
and is reported as such rather than as a result. Reading hwdec-current is what
showed that; the CPU delta alone looked like a finding.

Asking for a zero-copy mode explicitly:

  hwdec=d3d11va  -> hwdec-current = no      (software)
  hwdec=dxva2    -> hwdec-current = no      (software)
  hwdec=nvdec    -> "Unsupported hwdec: nvdec"
  hwdec=cuda     -> "Unsupported hwdec: cuda"

mpv prints why, in its own configuration line:

  -Dd3d11=disabled -Ddirect3d=disabled -Dgl-win32=disabled
  -Dgl-dxinterop=disabled -Degl-angle=disabled

Set to strip window output backends — "the framework's GL context is the only
display" — which also stripped the decode interops. Those are different things.

And enabling them would not help on Windows. The only zero-copy bridge that works
with a desktop WGL context is hwdec_dxva2gldx, and it is 8-bit by construction:

  #define SHARED_SURFACE_D3DFMT D3DFMT_X8R8G8B8
  mapper->dst_params.imgfmt = IMGFMT_RGB0;

A zero-copy path that throws away the ten bits phases 2 to 5 exist to carry. The
10-bit bridge is hwdec_d3d11egl, which needs an ANGLE EGL context; ANGLE is GL ES
over D3D11 and will not import Vulkan memory through GL_EXT_memory_object, so
taking it would cost the interop the whole design rests on.

VERDICT: zero-copy on Windows is incompatible with this architecture, not merely
unbuilt. Linux may differ — hwdec_cuda and hwdec_vaapi map the hardware format
and keep its subformat, so they carry 10 bits — and needs the same native build
change plus one unanswered question: whether CUDA-GL or VAAPI-EGL interop works
in a hidden GL context beside a Vulkan device.

Cost of learning this: two flags read and four runs, against rebuilding FFmpeg
and mpv first and finding out afterwards.

Why Vulkan costs more than GL on video, 2026-09-27
and why --syncbench said it did not
═══════════════════════════════════════════════════════

4K HEVC HDR, zero-copy decode on both, CPU per second:

  GL   (8-bit sRGB, no HDR video)                 56
  Vulkan, 8-bit sRGB swapchain (F16 off)         176
  Vulkan, scRGB + offscreen, SDR video           220
  Vulkan, everything on                          180

The ~120 ms/s appears with the Vulkan renderer at its SIMPLEST. So it is not the
half-float swapchain and not the offscreen pass, which is where it was first
guessed to be. (220 against 180 is run-to-run noise; the film streams over SMB.)

What it is, timed inside FinishExternalFrame under a real decode:

  per frame over 120: glFinish 0,740 ms, barrier 0,235 ms  ->  23 ms/s at 24 fps
  per frame over 120: glFinish 1,167 ms, barrier 0,282 ms  ->  35 ms/s
  per frame over 120: glFinish 4,174 ms, barrier 0,624 ms  -> 115 ms/s
  per frame over 120: glFinish 5,330 ms, barrier 0,640 ms  -> 143 ms/s

That is the whole gap.

--syncbench had measured this at 0,27 ms a frame and it was written off on that
number. The benchmark was not wrong about what it measured; it measured the wrong
thing. It timed a glClear on an otherwise idle GPU, so glFinish had nothing to
wait for — which is also why it came out FLAT between 1080p and 4K. A cost that
does not scale with the thing it should scale with is a warning about the
benchmark, and it was read as a reassuring result instead.

Fixable, and not blocked by SkiaSharp. glFinish is a CPU block; GL_EXT_semaphore
is the sharp version — export a VkSemaphore, import it into the GL context,
signal it with glSignalSemaphoreEXT after mpv draws, and have the barrier submit
wait on it. Skia is not part of this path at all, so the missing GRFlushInfo that
blocks the swapchain's acquire does not apply. Worth about 100 ms/s at 4K.
